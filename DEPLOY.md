# Обновление сайта — 1.4.0

## 1. GitHub и Render

Распакуйте архив. Загрузите содержимое папки проекта в корень `pongy-server`, заменяя совпадающие файлы и сохраняя структуру папок. ZIP в репозиторий загружать не нужно.

Не загружайте `.env`, `node_modules`, `data`, базы данных или реальные ключи. `.env.example`, `.gitignore`, `firestore.rules`, `lib`, `public`, `tests`, `.github`, `package.json`, `package-lock.json`, `server.js` и документацию загружать можно.

В Render → ваш сервис → Settings:
- Build Command: `npm ci`
- Start Command: `npm start`
- Node.js: 22 или новее.

В Environment оставьте существующие ключи и добавьте/проверьте:

```text
NODE_ENV=production
FRONTEND_URL=https://pongy-ai.devs.surf
GOOGLE_CALLBACK_URL=https://pongy-ai.devs.surf/auth/google/callback
COOKIE_SAMESITE=lax
TRUST_PROXY=1
FIREBASE_PROJECT_ID=pongy-ai-86e15
```

`OPENROUTER_API_KEY`, `FIREBASE_API_KEY`, `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET` остаются вашими существующими значениями. При 401 от OpenRouter замените его ключ в Render на действующий — код не может исправить недействительный ключ или лимиты аккаунта. Посетители сайта ключ не вводят.

`JWT_SECRET` и `SESSION_SECRET`: два разных случайных значения, каждое не короче 32 символов. Создайте их один раз и не меняйте при каждом обновлении. Не публикуйте их и не отправляйте в чат. При замене существующего секрета потребуется повторный вход.

`PUBLIC_API_ORIGIN` для текущего размещения не нужен: сайт и API обслуживаются одним сервером, запросы идут через домен сайта. Не переходите между доменом сайта и адресом Render во время авторизации.

## 2. Постоянная история на бесплатном Render

Без постоянного диска SQLite и автоматически созданные секреты могут исчезать при перезапуске или деплое. Для бесплатного облачного варианта:

1. Откройте Firebase Console → проект `pongy-ai-86e15`.
2. Build → Firestore Database → Create database. Используйте базу `(default)` и production mode, не открытый test mode. Выберите доступный регион.
3. Вкладка **Rules**: замените правила содержимым `firestore.rules`, нажмите **Publish**. Они разрешают доступ только к своим данным и только с подтверждённой почтой.
4. Authentication → Sign-in method: Email/Password должен быть включён. Включите также **Google**, если нужен вход Google с облачным сохранением. Укажите контактную почту проекта.
5. Authentication → Settings → Authorized domains: добавьте `pongy-ai.devs.surf`.
6. В Render добавьте `FIREBASE_FIRESTORE_ENABLED=true`; проверьте `FIREBASE_API_KEY`, `FIREBASE_PROJECT_ID` и постоянные секреты из шага 1.
7. Save → Deploy latest commit. Войдите на сайт заново один раз.

Чаты, настройки, вложения и записи сеансов будут храниться в Firestore. Существующие локальные чаты переносятся при первом входе с включённым облачным хранением, если они ещё не потеряны. Удалённые ранее с временного диска данные восстановить невозможно.

Firestore имеет бесплатную квоту, а не неограниченное хранение. При отказе облака сайт показывает ошибку, а не утверждает, что данные сохранены. Без Firestore используйте постоянный диск Render и `DATA_DIR` на этом диске.

Если пользователь прежде входил только в локальный аккаунт без Firebase, сначала зарегистрируйте ту же почту в Firebase и подтвердите её: после успешного входа аккаунт связывается. При включённом облаке старый локальный вход не обеспечивает облачный доступ.

## 3. Google: redirect_uri_mismatch

Google Cloud Console → APIs & Services → Credentials → **тот OAuth Client ID, который указан в Render** → Authorized redirect URIs:

```text
https://pongy-ai.devs.surf/auth/google/callback
```

Добавьте этот адрес точно, без пробелов и завершающего `/`. Authorized JavaScript origins:

```text
https://pongy-ai.devs.surf
```

Сохраните. Если OAuth-приложение находится в Testing, добавьте нужные аккаунты в Test users. Для Firestore включите Google и в Firebase Authentication; если Firebase не принимает токен существующего OAuth-клиента, сверяйте настройки клиента с Google-провайдером этого Firebase-проекта. Не используйте OAuth-клиент другого проекта.

## 4. Проверка после деплоя

Откройте сайт и обновите страницу с обходом кеша. Затем:
- Войдите, отправьте сообщение, обновите страницу: вход и история должны сохраниться.
- Прикрепите TXT или изображение: появится отдельная плашка, не случайный текст в поле ввода.
- Нажмите «Уточнить» под ответом, напишите дополнение, отправьте.
- Search выполняет поиск в Wikipedia, не общий поиск по всему интернету.
- В Настройках при необходимости включите контекст из других чатов.
- Проверьте почтовый вход и Google реальными аккаунтами.

Оплата остаётся заглушкой. Бесплатные модели и внешние сервисы не имеют 100% гарантии доступности. Реальные Google OAuth, доставка писем, квоты Firestore и качество ИИ проверяются после настройки ваших сервисов.

## 5. Новые возможности 1.4.0

Для ZIP, создания файлов, поиска Wiki и фотографий новые переменные не нужны. Достаточно существующего рабочего `OPENROUTER_API_KEY`. Выбор инструментов зависит от возможностей модели; приоритет отдаётся бесплатным моделям с поддержкой инструментов.

После замены файлов: GitHub → Commit changes; Render → Manual Deploy → Deploy latest commit. Дождитесь **Live**, затем обновите сайт с обходом кеша. Не удаляйте существующие переменные Environment и не меняйте секреты сеансов.

Проверьте запрос: «Найди фотографию кошки и Wiki-страницу, создай Python-файл и ZIP». Под ответом должны появиться вложения и раскрываемый список «Источники (N)». Фотографии ищутся в Wikimedia Commons, страницы — в Wikipedia. Это не общий поиск по всем сайтам. Список содержит полученные серверными инструментами источники, а не ссылки, придуманные моделью.

### Генерация новых изображений — необязательно

По умолчанию выключена. Поиск готовых фотографий работает без её включения.

1. В OpenRouter выберите доступную модель генерации изображений и проверьте цену/баланс. Установите лимит расходов для серверного ключа.
2. В Render → Environment добавьте:

```text
IMAGE_GENERATION_ENABLED=true
IMAGE_MODEL=bytedance-seed/seedream-4.5
```

Это пример модели из официальной документации, не обещание бесплатной генерации. Можно указать другую модель, поддерживающую `/api/v1/images`. Используется ваш существующий `OPENROUTER_API_KEY`.
3. Save и Deploy. Проверьте явный запрос «Нарисуй…». Для отключения верните `IMAGE_GENERATION_ENABLED=false`.

Лимиты приложения: одно изображение на ответ, три на пользователя в час, десять суммарно в час на процесс сервера. Они сбрасываются при перезапуске и не заменяют лимит расходов у провайдера. Реальная генерация с вашим ключом здесь не проверялась.

### Файлы и ограничения

- До 2 МБ на пользовательский файл; до четырёх вложений на сообщение.
- ZIP: до 100 элементов, 8 МБ суммарно после распаковки, 2 МБ на элемент. Вложенные архивы, зашифрованные ZIP, исполняемые бинарные файлы и небезопасные пути отклоняются.
- ZIP анализируется как текст/код и извлечённый текст PDF/DOCX. Изображения нужно загружать отдельно. `.env`, приватные ключи, зависимости и служебные каталоги исключаются. Скачиваемый обработанный архив — не полная копия оригинала; лимит 500 КБ.
- ИИ создаёт текстовые и программные файлы, CSV/JSON/Markdown/HTML и ZIP. Это не среда выполнения: созданный код не запускается и автоматически не тестируется. PDF/XLSX/DOCX на выходе не создаются.
- Неподдерживаемый формат отклоняется с уведомлением «Данный формат файлов не поддерживается». Текстовые файлы должны быть в UTF-8.
- Оплата Plus остаётся заглушкой. Доступность инструментов и качество ответа зависят от провайдера и выбранной модели.
